## What was delivered

PLAN.md §10 lists M6 as "ADR-0007 and ADR-0008, debug log export, error states, backup/restore
docs (including how to recover a damaged segment ...), user guide, release". All of it is
merged except the release itself.

- **The deferred features, planned** (#21). Both ADRs are Proposed and change no code.
  - [ADR-0007](../adr/0007-end-to-end-encryption-plan.md): end-to-end encryption as a codec,
    `aead1`, per backend: AES-256-GCM-SIV with a fixed nonce, so a segment always encrypts to
    the same file; segment names hashed with a separate name key; a random store key wrapped,
    in key files on the backend, by an Argon2id key from a passphrase; rotation, recovery,
    the metadata that stays visible, and moving to a new encrypted store rather than
    encrypting one in place. It checks PLAN §6.6's seam against `core:sync` and says what v1
    already keeps (every segment byte goes through `SegmentCodec`; a device leaves a backend
    with another codec's format file alone) and what the change will touch.
  - [ADR-0008](../adr/0008-multi-user-plan.md): sharing as *spaces*, each its own store with
    its own key; a space key wrapped to each member's X25519 key; revisions signed with
    Ed25519; no accounts and no login; pin and archive per person; a shared note is a copy
    with a new history. It needs ADR-0007 first, and lists what v1 makes hard and which v1
    decisions must stay.
  - PLAN.md §1, §6.6 and §8 and the ADR index point to them.
- **`core:logging`** (new, #23, [ADR-0021](../adr/0021-local-logging.md)): a small logger of
  the project's own, not Kermit, for the JVM, Android and `linuxX64`; a rotating file sink
  (256 KiB, four files, a POSIX lock per line, files 0600 in a 0700 directory), in
  `~/.local/state/jotter/logs/` (`desktop.log`, `cli.log`) and in Android's
  `noBackupFilesDir/logs`. Every line passes `redact`: URLs cut to scheme, host and port, the
  home directory as `~`, credentials replaced. Exceptions are logged by class and stack
  frames, with their message only for an allow-list of classes. It is the SLF4J provider, so
  Ktor's lines reach the log and the three "no providers" warnings seen in M4 are gone, and
  it bridges OkHttp's `java.util.logging`. Sync, WebDAV, the hub and its client, `app:sync`
  and the three apps log; never note text, titles, tags, secrets or credentials
  (`LogRedactionTest` drives real sync paths with marker strings). `JOTTER_LOG_LEVEL` changes
  the level for one run on Linux.
- **The debug log** (#23): `jotter debug-log [--output FILE]`, which works even when the notes
  cannot be opened; Sync, "Debug log", "Save to a file…" on the desktop, also offered by the
  window that says the notes cannot be opened; Sync, "Debug log", "Save…" through Android's
  document picker. It holds versions, platform, each backend's kind, last sync and issues, and
  the newest log lines, and is shown in full before it is saved. Jotter never sends it.
  ([guide](../guide/debug-log.md))
- **Error states** (#23): `StorageProblem` in `core:storage` tells ten database failures
  apart (locked, disk full, damaged, read-only, no access, disk error, newer version, another
  application's database, a failed upgrade, other), and each app puts them in plain words with
  what to do: the CLI, the desktop app, Android, the share target, sync status and hub status.
  A damaged file is never changed or replaced. The messages, and what to do about each, are in
  [troubleshooting](../guide/troubleshooting.md).
- **Export database** (#25): a checked single-file copy of the notes database while the app
  runs, as PLAN §1 promised. `NoteStore.exportTo` writes it with SQLite's `VACUUM INTO` and
  checks it (`integrity_check`, application id, schema version); `app:sync`'s
  `DatabaseExport` writes it to a hidden file beside the target, syncs it and renames it into
  place, never over the live database and never over a file without a yes. On the CLI,
  `jotter export-database FILE [--replace]`; on the desktop, File, "Export database…" and the
  foot of the Sync screen; on Android, the foot of the Sync screen, staged in the app's cache
  and written to the document the picker returns. Each says that passwords and pairing tokens
  are not in the copy.
- **Four fixes from writing the guide** (#25): Android's backend card names the Keystore, not
  a keyring; a missing or unreadable password has its own words and offers to enter it,
  instead of network advice; the editor's tags wrap below the tag field (tested at 320 dp); and
  Android's backup rules name `jotter.db` only, as Android adds its `-wal` itself, so the
  `-wal` is in a backup once instead of twice (checked with `bmgr` on API 36).
- **Entering a password again may move it** (#26, an amendment to
  [ADR-0016](../adr/0016-where-secrets-live.md)). A database restored on a computer with no
  Secret Service still names the keyring, so its password could never be entered there.
  `jotter backends password ID --store file|keyring`, and on the desktop the password dialog's
  offer of the file, write the new copy, record the new place
  (`BackendStore.updateSettings`), then delete the old copy, saying where it may stay if that
  fails. Without `--store`, a missing keyring is answered with the `--store file` command.
- **The user guide** (#24), nine pages under [docs/guide](../guide/README.md), linked from the
  README: install, notes, Keep import and Markdown export, the CLI, sync (USB folder, WebDAV,
  the PC hub over Tailscale), sync status and conflicts, the debug log,
  [back up and restore](../guide/backup.md), and troubleshooting. The backup page covers a
  damaged notes file and, as PLAN §10 asks, a damaged file on a backend (remove the backend on
  a device that still holds its revisions and add it again, ADR-0014), and what Android's own
  backup holds. Each page ends with what was checked and what was not.
- **A device-test retry** (#27). On API 26, #22's run 41812379147 reported 0 test cases for
  `core:sync`: the test runner's `adb` call failed before the test APK was installed, and AGP
  passed the task. The `android-device` job now runs `.github/scripts/device-tests.sh`, which
  runs once more only the modules that reported no test case. Failed tests are not retried,
  and `device-test-results.sh` still checks every module afterwards.
- **The Linux package and the release workflow** (#22,
  [ADR-0020](../adr/0020-linux-desktop-package.md)):
  - `Jotter-X.Y.Z-x86_64.AppImage`: the desktop app, the CLI and one Java runtime. `AppRun`
    runs the CLI when the first argument is `cli` or when started under the name `jotter`
    (a symlink on `PATH`), and the app otherwise. The CLI is also released alone as
    `jotter-cli-X.Y.Z.zip`, for Java 21 or newer. No Flatpak.
  - `--version` for the desktop app, and `app/desktop/scripts/smoke-appimage.sh`, which checks
    an AppImage headless with temporary directories, and its window on Xvfb with
    `JOTTER_SMOKE_GUI=1`.
  - `app/desktop/scripts/reproducible-build.sh` and the `desktop` job of `Reproducible`: two
    builds of one commit give the same AppImage and CLI zip, for the same JDK build and
    squashfs-tools version.
  - `.github/workflows/release.yml`: on a `v*` tag, or by hand as a dry run, it builds the
    unsigned APK, the AppImage and the CLI zip, smoke-tests the AppImage, writes `SHA256SUMS`
    and `BUILDINFO.txt`, and creates a **draft** release. It never publishes.
  - [RELEASING.md](../../RELEASING.md), moved from `docs/releasing.md` and extended to the
    AppImage, and [CHANGELOG.md](../../CHANGELOG.md), whose section for a version the workflow
    copies into the release.

## Issue #28, fixed by #34

The first full nightly simulator run, Actions run
[41815326464](https://github.com/sameerkrmishra/jotter/actions/runs/41815326464), failed:
[issue #28](https://github.com/sameerkrmishra/jotter/issues/28), seed 171987,
`ConvergenceTest`, an `IllegalStateException` in the test helper `ResolveNow.kt`. The next
four runs failed too (#29 to #32).
[PR #34](https://github.com/sameerkrmishra/jotter/pull/34), merged as `7462101`, fixed two
`core:sync` bugs behind them:

- **A note deleted beside other heads** (seeds 171987, 218876, 330375 and 374916; #28, #29,
  #31, #32). `deleteForever` removed the note's row while another head, hidden for a missing
  ancestor, had become the head to show, so the note left the list until the next sync, and
  answering its hidden head named no shown head. Now `core:sync` reconciles the note in the
  deletion's own transaction, through `SyncStore.settleNotesWith`.
- **A merge pass that stopped too early** (seed 262796, #30). A merge made by the fold could be
  the missing parent that proves another revision invalid; a deletion under it then became
  live after the fold had passed, and the note kept two heads for good. Now the fold repeats
  until it makes nothing new ([ADR-0013](../adr/0013-merge-base-and-covered-heads.md),
  amended).

No merge's bytes change (the pinned digests are unchanged). All five seeds are pinned in
`ConvergenceTest`'s `REGRESSION_SEEDS`, and `LostHistoryTest` has a focused test for each fix.
#34 reports seeds 150000 to 199999 passing. The nightly issue now names every failing seed and
the command that replays it. No nightly has run since the merge.

Issues #28 to #32 are still open, for the maintainer to close now that #34 is merged.

## Decisions made

ADR-0007, ADR-0008, ADR-0020 and ADR-0021 are Proposed: written and reviewed by agents, not
accepted by the maintainer. Decisions marked **(orchestrator)** were made by the orchestrator
on the maintainer's behalf, for review at the end of the project
([PLAN.md §9](../PLAN.md#9-development-model-agent-swarm)).

The deferred features:

- **(orchestrator)** [ADR-0007](../adr/0007-end-to-end-encryption-plan.md): **a deterministic
  AEAD codec**, AES-256-GCM-SIV with a fixed nonce, so that content naming, `writeNew` and a
  repair that writes the same bytes keep working; it reveals only whether two files hold the
  same segment, which their names already show. GCM-SIV and Argon2id are not in the JDK: Bouncy
  Castle on the JVM and Android, OpenSSL 3.2 or later on `linuxX64`, a new dependency when it
  is built. It replaces PLAN.md's XChaCha20 example.
- **(orchestrator)** ADR-0007: **an existing store is not encrypted in place**; the user makes
  a new, encrypted store and removes the plain one by hand. The device's own database, exports
  and logs stay plain: disk encryption is the operating system's job.
- **(orchestrator)** [ADR-0008](../adr/0008-multi-user-plan.md): **shared spaces as separate
  stores**, keys wrapped to each member instead of a shared passphrase, no accounts or login
  in Jotter (a shared tablet uses the system's user profiles), and one person per device
  database.

Logging and errors:

- **(orchestrator)** [ADR-0021](../adr/0021-local-logging.md): **a logger of our own, not
  Kermit** as PLAN.md had planned, since Kermit has no file sink and its platform writers are
  not wanted; and **one process-wide `Logging`**, an exception to ADR-0005's constructor
  injection. PLAN.md §3.2 and §3.4 now say so.
- **(orchestrator)** ADR-0021: **exception messages only for an allow-list of classes**, as a
  pattern cannot recognise note text; SLF4J's TRACE is dropped, as Ktor puts URLs and headers
  there. Android's log is in `noBackupFilesDir`, never backed up.
- **(orchestrator)** Without an ADR, in `StorageProblem` and the [troubleshooting
  page](../guide/troubleshooting.md): **Jotter never changes or replaces a damaged database**;
  it says so and points to a backup or to starting fresh and letting sync bring the notes back.

Backup and secrets:

- **(orchestrator)** Without an ADR, in `NoteStore.exportTo` and `DatabaseExport` (#25):
  **Export database is `VACUUM INTO`, checked, then renamed into place**, refusing the live
  database and an existing file unless the user agrees. There is no import: a copy is
  restored by putting the file in place with Jotter closed, and not at all on Android.
- **(orchestrator)** ADR-0016, amended (#26): **entering a secret again may move it** between
  the keyring and the file, written first, recorded second, the old copy deleted last.

Packaging and release:

- **(orchestrator)** [ADR-0020](../adr/0020-linux-desktop-package.md): **an AppImage, not a
  Flatpak**, for v1.0, because Flatpak's sandbox breaks folder backends typed as paths (USB
  sticks), gives the app and the CLI two databases and two secrets files, and needs grants for
  the keyring; and Flathub builds offline. PLAN.md §10 allowed either.
- **(orchestrator)** ADR-0020: **the CLI inside the AppImage**, chosen by the name it is started
  under, and also alone as a zip. Through the AppImage it starts in about 450 ms against about
  146 ms for the zip (ADR-0020's measurements), as JDK 21 does not write a CLI class data
  archive deterministically and one is therefore left out.
- **(orchestrator)** ADR-0020: **AppImage's `type2-runtime` pinned** to release 20251108 by
  SHA-256 and packed with mksquashfs directly, not appimagetool; **no update information**
  embedded, as the app contacts nothing but its backends; the release built on a pinned
  `ubuntu-24.04` runner, with the JDK and squashfs-tools written to `BUILDINFO.txt`.
- **(orchestrator)** `release.yml` and [RELEASING.md](../../RELEASING.md): **CI makes a draft
  only**; signing and publishing stay with the maintainer, whose key never reaches CI.

CI and process:

- **(orchestrator)** Without an ADR, in `device-tests.sh` (#27): **a module that ran no test is
  run once more**; a failed test is never retried.
- **(orchestrator)** Without an ADR: #21 to #27 and #34 were merged with merge commits, as in
  M4 and M5, in the order of the table. #22 merged `main` into its branch last (`cf3f047`) before
  its merge.

## Known limitations and what was not verified

What has not been verified:

- **The exit criterion**: no tag, no release, no signed APK, and `release.yml` has never run on
  `main` or on a tag, nor created a draft release.
- **The nightly simulator after #34**: no nightly run has passed yet. The API 26 flake on
  `main` after #22 (above) was not investigated.
- **The exit criteria of M4 and M5**, and with them a real WebDAV provider, a real phone, a real
  tailnet, Tailscale's Android app and WebDAV over TLS from Android.
- **The AppImage on a real desktop**: its window opened only on Xvfb, in CI's smoke test and for
  the guide. Menu integration (Gear Lever, AppImageLauncher) was not tried, nor a machine
  without FUSE.
- **Android's document picker** for the debug log and Export database: run by hand on an
  emulator for the guide, not driven by device tests, never on a phone.
- **Android backups**: Android 9 to 11 (`xml-v28`), Google's real backup and device transfer
  were not run; only `bmgr` to the local transport on API 36, and API 26 (nothing backed up).
- From the guide's own "Checked" sections: installing an APK from a phone's browser, Android
  background sync, a real Google Takeout, and losing `hub-devices.json`.
- **The desktop's File menu in a real window** (#25).
- **F-Droid**: the recipe's TODOs (`commit`, `AllowedAPKSigningKeys`, the JDK lines), `fdroid
  lint`, `fdroid build` and `fdroid scanner`, and screenshots. Nothing has been submitted.

Known limitations:

- **No end-to-end encryption and no sharing**: ADR-0007 and ADR-0008 are plans. Whoever can read
  a backend, the hub's folder or a lost USB stick can read every note and its history.
- **No Flatpak**, no automatic updates, x86_64 only. The AppImage needs FUSE, or
  `--appimage-extract-and-run`. It is not sandboxed. Its CLI is slow in a loop.
- Reproducing CI's AppImage byte for byte needs CI's JDK build and squashfs-tools; the APK
  needs only JDK 21.
- **The Android app cannot load an exported copy back**; it can be read or restored on a
  computer.
- A restored database never brings passwords or tokens: they are entered again, and a hub's
  phone must be paired again.
- **The debug log can show folder paths** outside the home directory, such as a USB stick's;
  the user reads it before saving. Redaction is pattern-based and a credential in an unexpected
  shape could pass; an exception message outside the allow-list is lost.
- The logs are at most about 1 MiB per app; older lines are dropped.
- The version is still `0.1.0`. A forgotten `versionCode` bump is caught only by Android or
  F-Droid (M5).
- From M5, still true: no local folders on Android, nothing backed up on Android 8, R8 off,
  another app's VPN in `100.64.0.0/10` passes the Tailscale check, and pairing means typing a
  long token.
