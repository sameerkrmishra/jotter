# M3: Sync engine

Status: built and tested, and **not closed**. The exit criterion is met in the
simulator, within the limits below. Sync is not wired into the apps yet: nobody can
sync two real devices until M4.

All of M3, the conflict UI and this note included, is in
[draft PR #12](https://github.com/sameerkrmishra/jotter/pull/12) (`m3/core-sync`),
which also holds M1 and M2. Its CI is green at `eb8f544`
([run 41614587678](https://github.com/sameerkrmishra/jotter/actions/runs/41614587678)):
`check` passed in 25 m 5 s and `simulate` in 8 m 13 s. `./gradlew check` also passed
locally on the same code; its JVM tests of `core:sync` and `app:shared-ui` came from
Gradle's build cache, and the `linuxX64` tests ran. No human has reviewed any of it
([PLAN.md §9](../PLAN.md#9-development-model-agent-swarm)). Figures were checked on
2026-11-03.

## What was delivered

- **`core:merge`**: the three-way line merge of `body` and `title`. Pure Kotlin, no
  I/O. Changes to touching lines merge, and identical insertions count once
  ([ADR-0011](../adr/0011-touching-changes-and-merge-format.md)). The diff has a
  search limit, so a large body costs linear work.
- **`backend:api`**: the `BlobStore` interface (`list`, `read`, `writeNew`, `ping`)
  and its failure types. **`backend:api:contract`**: the contract suite every
  backend must pass, and `InMemoryBlobStore` for tests.
- **`backend:localfolder`**: a `BlobStore` over a directory, such as a USB stick.
  It publishes with a hard link, or with a lock file and a rename where hard links
  are missing, as on FAT. A marker file tells a store from an empty mount point
  ([ADR-0012](../adr/0012-local-folder-publishing.md)).
- **`core:sync`**: push, pull and apply over a `BlobStore`; automatic merges with
  hashed ids; covered heads; conflicts, hidden heads and text that does not count;
  `ConflictResolver` for the UI; and the convergence simulator
  ([ADR-0013](../adr/0013-merge-base-and-covered-heads.md),
  [ADR-0014](../adr/0014-sync-failure-handling.md)).
- **`core:storage`**: schema version 2, with the sync tables, a migration from
  version 1, the note size cap and `SyncStore`, which only `core:sync` may use.
- **`app:shared-ui` and `app:desktop`**: a "Needs attention" view and a review
  screen for each note that sync left something on. The user can keep the shown
  version, keep the other, keep both, or combine by hand. Texts being combined are
  kept across restarts.
- **`app:cli`**: `jotter conflicts` lists what sync left, and `jotter conflicts ID`
  prints every version of one note. It only reads.
- **CI**: a `simulate` job beside `check`, and a nightly workflow.

## Exit criterion (PLAN.md §10)

| Criterion | Result | Evidence |
|---|---|---|
| Property-based tests: N simulated devices with random offline edits always converge | Met, for what the simulator models | `ConvergenceTest`: seeds 1 to 800 in `check` on the JVM, 10 on `linuxX64`, 34 regression seeds on both; seeds 1 to 3000 in CI's `simulate` job. The nightly has never run |

### What the simulator models

`Simulation` in `core:sync` runs real SQLite databases over in-memory backends.
Everything in a case comes from one seed, so a failing seed replays. A case has:

- 2 to 5 devices, and up to 2 more started from a backup. Device 0 is on every
  backend and relays between them; each other device is on one. Device 0 never dies;
  others can die for good.
- 1 to 3 backends.
- 30 to 139 steps of random actions: create, edit, pin, state, tags, delete
  forever, imports of one source note on several devices, partial syncs, crashes,
  restarts, forgetting a backend and adding it again, backups and restores (also of
  a whole disk with a backend on it), and conflicts answered at random in all four
  ways.
- Faults: failed `list`, `read` and `writeNew`, a write that fails after it
  published, outages, files held back from a listing, lost segments, damaged files
  from strangers, sound files under a wrong hash, forged merges, revisions with bad
  stamps, and claims to resolve a conflict from a revision that does not count.
- Device clocks that start up to an hour apart.

Then the faults stop and the living devices sync until a round changes nothing.
The test then asserts that every device holds the same revisions, live heads,
notes, open conflicts and hidden heads; that once everything is answered each note
has one live head and shows it; that no forged merge or bad stamp counts; that
every stored merge follows from its parents when computed again; and that no line
of a body and no title is lost without a user's edit, resolution or deletion
explaining it (`LineHistory`, which uses none of the code under test). Each case
ends with a conflict that a bad revision claims to resolve and that one device
deletes while another edits; it must stay open until answered. The run also fails
if its cases made no more merges than there are cases, or no conflict or crash.

### Where the seeds run

| Where | Seeds | Platform |
|---|---|---|
| `./gradlew check` | 1 to 800, and the 34 `REGRESSION_SEEDS` | JVM |
| `./gradlew check` | 1 to 10, and the 34 `REGRESSION_SEEDS` | `linuxX64` |
| CI `simulate` job | 1 to 3000 | JVM |
| `nightly.yml` | 50000 a night, from `100000 + run × 50000` | JVM |

The regression seeds are the first catches of every bug and mutant found so far;
seven of them are above 800. On the JVM the seeds run one per core.
`simulate` and the nightly use `core/sync/scripts/simulate.sh`, which fails unless
the test report names exactly the range asked for. `check` itself does not use the
script.

To run a range by hand (this one was run for this note):

```sh
core/sync/scripts/simulate.sh 1 20
```

It printed `Simulated seeds 1 until 21: 369 revisions, 93 merges, 21 conflicts, 14
crashes, 43 bad revisions, 25 restored backups, 3 of them whole disks`. The
`core:sync` README has the timings: on a GitHub runner about 11 seeds a second.

### What it does not cover

- **Real backends.** Backends are in memory. The local folder passes the same
  contract suite, and races between processes, in its own tests, but it is not in
  the simulator. There is no WebDAV yet.
- **Real devices and real time.** All devices of a case run in one process, on one
  thread, each with its own database. No scheduling, no two processes on one
  database, no Android.
- **The apps.** No UI or CLI code runs in the simulator. The review screen has its
  own tests against two real databases.
- **Text.** Lines are short, unique and from a small vocabulary. A note starts with
  one to six. Large bodies, line endings and odd Unicode are covered by `core:merge`'s
  property tests instead.
- **Decay of a published file**, and a merge with wrong text under a valid hash.
  Both are known limits ([ADR-0014](../adr/0014-sync-failure-handling.md)), not
  faults the simulator makes.
- **More devices or backends** than above, and any seed not yet run.

## Demo

Sync has no caller in any app yet. There is no way to add a backend, and nothing
syncs. Backend management, the `backend` table and scheduling are M4. So a user can
do today what M2 allowed, plus `jotter conflicts`, which finds nothing in a database
that never synced. The desktop app's "Needs attention" view is empty for the same
reason. Conflicts, waiting edits and set-aside text are shown only in tests.

You need the prerequisites in [CONTRIBUTING.md](../../CONTRIBUTING.md), and `java`
21 or newer to run the CLI. Run the Gradle steps first, in your normal shell:

```sh
./gradlew :app:cli:installDist
core/sync/scripts/simulate.sh 1 20     # the simulator, as above
./gradlew :app:shared-ui:jvmTest --rerun --tests '*ReviewScreenTest*'   # 17 tests
./gradlew :app:cli:test --rerun --tests '*ConflictsCommandTest*'         # 4 tests
```

`ReviewScreenTest` makes each case with a second real database synced through an
in-memory backend, answers it on the screen without a display, and checks the
result. `twoDevicesConvergeOnWhatTheUserCombined` then syncs both devices and finds
the same note on each. `ConflictsCommandTest` makes a conflict, a waiting edit and set-aside text the same
way, and checks what `jotter conflicts` prints for each.

Then the CLI, with a throwaway `HOME` and database:

```sh
scratch=$(mktemp -d)
mkdir "$scratch/home"
export HOME="$scratch/home" JOTTER_DB="$scratch/notes.db" XDG_CACHE_HOME="$scratch/cache"
jotter=app/cli/build/install/jotter/bin/jotter

id=$($jotter add --title "Shopping" "- [ ] milk
- [ ] bread")
$jotter conflicts          # prints nothing: nothing has synced
$jotter conflicts "$id"    # prints an empty line: this note has nothing to review
$jotter conflicts nope     # jotter: no note with id nope, status 1
head -c 5000001 /dev/zero | tr '\0' a | $jotter add -
                           # jotter: the note is too long: A note can hold 5000000
                           # characters, not 5000001, status 1
head -c 5000000 /dev/zero | tr '\0' a | $jotter add -   # stored
```

Remove the scratch directory with `rm -r "$scratch"`, and start a new shell for
Gradle, as `HOME` now points into it.

The desktop app was not started for this note.

## Decisions made

ADR-0012, 0013 and 0014 are Proposed: written and reviewed by agents, not accepted
by the maintainer. ADR-0011 is Accepted. Decisions marked **(orchestrator)** were
made by the orchestrator on the maintainer's behalf, for review at the end of the
project ([PLAN.md §9](../PLAN.md#9-development-model-agent-swarm)).

- [ADR-0011](../adr/0011-touching-changes-and-merge-format.md): touching changes
  merge, unlike in git, because ticking neighbouring checklist items must not be a
  conflict. The merge rules and the diff limit are part of the sync format, as merged
  text is hashed.
- [ADR-0012](../adr/0012-local-folder-publishing.md): the local folder publishes with
  a hard link, or under a lock file where there are none, so `writeNew` never
  replaces a file on FAT either. A marker file, written only when the user adds the
  folder, keeps an unplugged stick from reading as an empty store.
- [ADR-0013](../adr/0013-merge-base-and-covered-heads.md): the merge base is the
  highest-stamped best common ancestor, not a recursive merge, because the rare
  extra conflict loses nothing and a recursive merge fixes much more format.
  A merge whose user revisions another head also has is "covered" and does not
  count, because without this devices out of step merge each other's merges for
  ever.
- **(orchestrator)** [ADR-0014](../adr/0014-sync-failure-handling.md): a segment's
  name is its number and a hash of its content, so a path has one possible
  content and nothing can overwrite anything. Pull tracks names read, not
  numbers.
- **(orchestrator)** [ADR-0014](../adr/0014-sync-failure-handling.md): bad revisions
  are not rejected. Every readable revision is stored and relayed, and whether it
  counts is judged from the revision and its ancestors alone, per revision, not per
  segment. So the verdict does not depend on arrival order, and devices end up with
  the same revisions.
- **(orchestrator)** [ADR-0014](../adr/0014-sync-failure-handling.md), amending
  [ADR-0004](../adr/0004-immutable-change-segments.md): a device restored from a
  backup keeps its id and reads the files in its own folder that it does not
  remember, so its lost tail comes back. A folder may now have several writers after
  a database was copied; content names keep them from overwriting each other.
- **(orchestrator)** [ADR-0014](../adr/0014-sync-failure-handling.md): a note is
  capped at 5,000,000 UTF-16 units of title and body, checked when a note is
  created, edited or resolved, so editing cannot make a note that can never sync. An
  import over it is skipped and reported, and a merge past it is a conflict.
- **(orchestrator)** [ADR-0014](../adr/0014-sync-failure-handling.md): received
  merges are not derived again. A merge with wrong text but a valid hash goes
  unnoticed. A user's devices run the same code, so such a merge is a bug that would
  derive the same text again.
- **(orchestrator)** [ADR-0014](../adr/0014-sync-failure-handling.md): bit rot in a
  file after it was published is a known limit. Readers report it as `CORRUPT` on
  every cycle. The recovery is to remove the backend on a device that holds those
  revisions and add it again (`SyncEngine.forget`), which pushes them in new files.
  M6's backup docs are to describe it.
- **(orchestrator)** [ADR-0014](../adr/0014-sync-failure-handling.md): text that does
  not count can be saved as a note or dismissed, and that is recorded on this device
  only (`dismissed_invalid`). A synced dismissal would need a new kind of revision.
- **(orchestrator)** [ADR-0014](../adr/0014-sync-failure-handling.md): texts being
  combined by hand are kept on this device (`combined_draft`), so they survive a
  restart. They are not synced, and the answer that uses one deletes it.
- **(orchestrator)** Without an ADR, in [ci.yml](../../.github/workflows/ci.yml):
  the `check` job's timeout is 45 minutes, against a measured 27.5, and the 3000-seed
  run is a separate `simulate` job, so that `check` stays near its length. Only
  `check` is a required status check on `main`.
- [ADR-0014](../adr/0014-sync-failure-handling.md): an answer to a conflict or hidden
  head names the head the user saw, and nothing is written if the note shows another
  by then, so a newer edit is never replaced unseen.
- [ADR-0014](../adr/0014-sync-failure-handling.md): hidden heads. A note never merges
  on partial history, as no device can tell that nobody holds the rest. Every live
  head with text that the note does not show is listed with its text and reason,
  until it merges or the user settles it with `ConflictResolver.settleHidden`, which
  writes a revision on the shown head. An edit is never hidden in silence.
- [ADR-0014](../adr/0014-sync-failure-handling.md): repairs. A device writes again,
  under the same name, a published segment of its own that is missing from its
  folder. A file that was read and is gone from a listing leaves the read set, and
  its revisions count as not on the backend, so the reader pushes them under its own
  name.
- [ADR-0014](../adr/0014-sync-failure-handling.md): an empty listing from a reachable
  store is believed, as `BlobStore` promises. Every file read there then counts as
  lost, and the device pushes what it holds: duplicates, no lost data.
- [ADR-0014](../adr/0014-sync-failure-handling.md): a file is at most 32 MiB,
  compressed or inflated, and inflating stops at the limit. A push splits revisions so
  that each segment fits, and a pull applies in batches of about 32 MiB.
- Without an ADR, in the [`core:sync` README](../../core/sync/README.md): `okio` gives
  SHA-256 and gzip in common code.

## Known limitations and what was not verified

What has not been verified:

- **Real FAT and exFAT.** The rename fallback was tested by disabling `link` on the
  temporary directory's file system, not on a FAT or exFAT mount.
- **Android.** No device run of any M3 module. Whether `fcntl` locks work on Android
  storage is unconfirmed; if not, the local folder cannot write there. The Android
  host tests of `core:sync`, `core:storage` and `app:shared-ui` are disabled.
  `backend:localfolder` runs its host tests on a host JVM, not on Android's own
  `java.nio`. *Verified in M5*, on API 26 and 36 emulators in CI's `android-device`
  job: `core:sync` (with 30 simulator seeds), `core:storage` and
  `backend:localfolder` pass on the device. An app has no hard links in its own
  storage (`EACCES`) or in shared storage, so the local folder always publishes by
  rename, and `fcntl` locks hold between processes on both. A link error crashed
  `writeNew` on Android before M5 fixed it: Android's `getFileStore` throws
  `SecurityException`. `app:shared-ui` and `content://` folders remain untested.
- **The nightly.** It has never run: scheduled workflows run only from the default
  branch, and `nightly.yml` is not on `main`.
- **One mutant.** `core/sync/scripts/mutants.py` lists 72 source mutations. The results of the
  latest runs are not committed. The run of `lost file stays read` was stopped by a
  permission refusal, so it is not known whether the tests catch it.
- **The desktop app in a window.** It was not started for M3. The review screen and
  the "Needs attention" view were only run headless, with `runComposeUiTest`.
- **NFS, `nolock` and FUSE mounts.** What ADR-0012 says about them is from knowledge
  of those systems, not tested. Real `EIO` from `readdir` and directory `fsync` was
  checked once by hand, outside `check`.
- **Duration.** `check` took 25 m 5 s on CI at `eb8f544`, and 26 m 9 s at
  `5ae8c50`, most of it building and
  running the native tests.

Known limitations:

- No sync in the apps (M4). `jotter conflicts` only reads; answers are the desktop
  app's.
- A merge with wrong text and a valid hash, and a file that decays after it was
  published, go unnoticed or stay reported for good (see the decisions above).
- A relay carries one copy of a collided revision id, so devices can disagree while
  that lasts. It takes a repeated random id, so a bug.
- A segment that nobody living read, lost after its writer died, is gone. Notes that
  build on it wait as hidden heads until the user settles them.
- Invalid revisions stay stored and are relayed for good. `MISSING` is reported on
  every cycle for a permanent hole. A user revision whose parent never arrives can
  never be judged, so it counts.
- A corrupt file costs a read on every cycle, and `sync_read` grows by a row per file.
  Every note's history is judged on each reconcile, and covered heads stay in the
  DAG, so cost grows with history.
- A criss-cross history conflicts more often than under a recursive merge. The fold
  order over three or more heads can change a clean text. Two touching edits may not
  read well together, and a clean merge can keep a line twice.
- Android `content://` folders are not supported by the local folder. On a system
  that translates error messages, exFAT through FUSE fails every write on the JVM.
  Stale temporary files are never removed.
- A merge of a very large body takes seconds and must not run on the UI thread.
  Crafted colliding lines are quadratic on Native.
- A segment that cannot be read is not about one note, so the UI does not show it
  until M4's backend screens.

## What M4 needs from M3

- **A `backend` table** (PLAN.md §4), as a schema migration. `core:sync` uses an
  opaque `backend_id` until then.
- **Scheduling and wiring.** `SyncEngine.sync` runs one cycle; the caller decides
  when. The desktop app needs a timer, sync after edits and on start, and backoff for
  `Unreachable`.
- **Adding and removing backends.** Adding a local folder calls
  `LocalFolderBlobStore.initialize()` once, and never because `ping` said
  `NOT_INITIALIZED`. Removing one calls `SyncEngine.forget`.
- **Showing `SyncReport` and `SegmentProblem`s** per backend, including `CORRUPT` and
  `MISSING`, which the review screen does not show.
- **`backend/webdav`** must pass `backend:api:contract`, including `writeNew` failing
  on an existing path (`If-None-Match: *`), and must never read an unreachable server
  as empty.
- **The nightly**, once on `main`: its first runs, and an answer to any issue it
  opens.
