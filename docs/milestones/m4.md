## What was delivered

- **`backend:webdav`**: a `BlobStore` in a collection on a WebDAV server, over
  Ktor's CIO client, on the JVM, Android and `linuxX64`. `writeNew` is `PUT` with
  `If-None-Match: *`. `list` walks `PROPFIND` with `Depth: 1` and returns all or
  fails. A marker file, `.jotter-store`, tells a store from an empty collection.
  Adding a store checks that the server refuses to replace a file. Plain `http` is
  refused except to loopback. A refused password is
  `UnreachableReason.UNAUTHORIZED` ([ADR-0017](../adr/0017-webdav-backend.md)).
- **`backend:peer`**: the client of the PC hub, on the JVM, Android and `linuxX64`.
  It holds the protocol, `PeerProtocol`, that the server shares. It sends its token
  only to loopback or Tailscale addresses, and reads answers strictly
  ([ADR-0015](../adr/0015-pc-hub-peer-protocol.md)).
- **`server`**: the hub, `PeerHub`. It serves a folder on the PC over HTTP on
  loopback or a Tailscale address, with a token per paired device, stored as a hash,
  and hard limits on connections, threads, memory and time. JVM only, on the JDK's
  blocking sockets (ADR-0015, amending
  [ADR-0006](../adr/0006-native-compatible-shared-modules.md)). The PC syncs with the
  same folder as a local folder backend.
- **`app:sync`** (new): the backend list and settings, adding and removing local
  folders, WebDAV servers and the hub, status in plain words, `SyncScheduler` for the
  desktop app, and where secrets live: `SecretServiceStore` through `secret-tool`, and
  `SecretFileStore`, a 0600 file the user may choose
  ([ADR-0016](../adr/0016-where-secrets-live.md)). It builds for `linuxX64` too, as the
  CLI uses it.
- **`core:storage`**: schema version 3, with the `backend` table, by a migration from
  version 2. `observeRevisionMark` tells the scheduler that a revision was stored.
- **`core:sync`**: the format file is now `jotter/formats/1-json+gzip.json`, one path
  per format and codec (ADR-0017, amending
  [ADR-0004](../adr/0004-immutable-change-segments.md)). `forgetUnlisted` drops the
  sync records of backends that another process removed.
- **`backend:api`**: `UnreachableReason.UNAUTHORIZED`, and a contract test for it,
  which only backends with credentials run.
- **`app:shared-ui` and `app:desktop`**: the Sync screen. It lists each backend with
  whether it can be reached, its last sync, its issues and where its password is kept.
  It adds a folder, a WebDAV server or the PC hub, asks before setting up a store,
  offers the password file when no keyring answers, takes a new password, removes a
  backend, and has "Sync now". The hub can be run on this PC from the same screen,
  with pairing and unpairing. The desktop app syncs on start, 5 s after edits, every
  5 minutes and on demand.
- **`app:cli`**: `jotter sync`, and `jotter backends` with `add` (a folder,
  `webdav URL --user NAME` or `peer HOST[:PORT]`), `password`, `remove` (with
  `--keep-secret`) and `status`. Passwords and tokens are read from the terminal or
  stdin, never from an argument.
- **CI**: a `webdav` job beside `check` and `simulate`, which runs
  `backend/webdav/scripts/live-test.sh` against lighttpd, Apache and rclone in
  containers, on the JVM and `linuxX64`. Only `check` is a required status check.

### Checklist for the maintainer: mailbox.org

Nothing about mailbox.org's WebDAV has been tested by this work: its URL, its
`If-None-Match`, its answers and whether it takes an app password over Basic
authentication are unknown (ADR-0017, "Not verified"). Write down what each step
prints, especially any refusal: it is the result.

1. **Make an app password.** In mailbox.org's web settings, create an
   application-specific password for Jotter. Where that setting is, and whether such a
   password works for WebDAV (Drive) as well as for mail, was not checked. One password
   per desktop lets each be revoked alone.
2. **Make an empty folder** in mailbox.org's Drive, for example `Jotter`. Jotter never
   creates the store's own collection.
3. **Find the WebDAV URL of that folder.** It is not known to this work, and is not
   guessed here. mailbox.org's help pages, or the Drive's own settings, give the
   WebDAV address of the Drive; the folder's URL is that address followed by
   `Jotter/`. It must be `https`. To check it, this must print `207`:

   ```sh
   curl -s -o /dev/null -w '%{http_code}\n' -u 'you@mailbox.org' -X PROPFIND -H 'Depth: 0' 'URL'
   ```

4. **Desktop A.** From the repository root, build the CLI and the app, and make
   `jotter` mean the CLI in this shell (the desktop binary is also called `jotter`).
   Use a database of its own, or a fresh machine. Install `secret-tool` (`libsecret`)
   so that the password goes to the keyring.

   ```sh
   ./gradlew :app:cli:installDist :app:desktop:createDistributable
   alias jotter="$PWD/app/cli/build/install/jotter/bin/jotter"
   export JOTTER_DB=~/jotter-m4/notes.db
   ```

   Then either open the app
   (`app/desktop/build/compose/binaries/main/app/jotter/bin/jotter`, from the same
   shell so that it gets `JOTTER_DB`), Sync, "Add server", with the URL, the
   mailbox.org address and the app password, and agree to set it up; or:

   ```sh
   jotter backends add webdav 'URL' --user you@mailbox.org --new   # asks for the password
   ```

   The alias was checked in zsh with `:app:cli:installDist`, a throwaway `HOME` and
   database: `jotter backends` ran, and an `https` URL with nothing listening was
   refused as "Cannot reach".

   Setting up writes a test file twice and needs the server to refuse the second
   write. If it refuses mailbox.org as a server that replaces files, stop: that ends
   the criterion for now, and is worth an issue.
5. **Desktop B, on another machine (step 7 needs it), with a separate database**,
   built and set up as in step 4: add the same URL **without** `--new` (in the app, it is added
   without the set-up question). It must not say "not a Jotter store yet".
6. **Edit.** On A, add a note `Packing` with the lines `passport` and `charger`.
   Wait for a sync (5 s after typing stops), or press "Sync now", or run `jotter sync`.
   On B, after a sync, the note is there. Edit it on B (tick or add a line), sync, and
   see the edit on A.
7. **A conflict.** Disconnect B from the network. On B, change `charger` to
   `sunscreen`. On A, change `charger` to `adapter`, and let A sync. Reconnect B and
   press "Sync now", then sync A again. Both must show `Packing` under "Needs
   attention", and `jotter conflicts` must list it on both. Answer it on one device
   (any of the four answers), sync both, and it must be gone on both.
8. **Declare convergence** when, after a final `jotter sync` on each:
   - `jotter sync` prints `synced` on both, and `jotter backends status` shows
     `reachable: yes` and no `issue:` lines;
   - `jotter conflicts` prints nothing on both;
   - `jotter export DIR` on each gives two directories that `diff -r` finds equal;
   - on mailbox.org, `jotter/formats/1-json+gzip.json` and one folder per device under
     `jotter/devices/` exist, beside `.jotter-store` in the collection.
9. **Optional.** A wrong app password (`jotter backends password ID`) is refused
   before it is stored; revoking the app password at mailbox.org makes the next sync
   end as `unauthorized`.
10. **Afterwards.** `jotter backends remove ID` on each, revoke the app passwords,
    and delete the `Jotter` folder by hand if it is not wanted.

This is also the first time the desktop app is opened in a real window since M2.

## Demo

Everything here was run for this note, from the repository root, with a throwaway
`HOME`, XDG directories and databases, and no session bus, so no keyring was
touched. You need the prerequisites in [CONTRIBUTING.md](../../CONTRIBUTING.md), and
`java` 21 or newer to run the CLI.

```sh
./gradlew :app:cli:installDist
scratch=$(mktemp -d)
mkdir "$scratch/home" "$scratch/stick" "$scratch/keepA" "$scratch/keepB"
export HOME="$scratch/home" XDG_CACHE_HOME="$scratch/cache" \
    XDG_CONFIG_HOME="$scratch/config" XDG_DATA_HOME="$scratch/data"
unset DBUS_SESSION_BUS_ADDRESS
jotter=$PWD/app/cli/build/install/jotter/bin/jotter
a() { JOTTER_DB="$scratch/a/notes.db" "$jotter" "$@"; }   # desktop A
b() { JOTTER_DB="$scratch/b/notes.db" "$jotter" "$@"; }   # desktop B
```

### Two databases through a local folder

```sh
a backends add "$scratch/stick"
    # jotter: ... is not a Jotter store yet. Setting it up creates a hidden file
    # .jotter-store there, ... To set it up, run: jotter backends add --new ..., status 1
a backends add --new --name Stick "$scratch/stick"   # prints the backend's id
b backends add --name Stick "$scratch/stick"         # no --new: A set it up
a backends            # id, Stick, the path, never, never

id=$(a add --title "Shopping" "- [ ] milk
- [ ] bread")
a sync                # ... Stick  synced  Synced. Received 0 changes, sent 1 file.
b sync                # ... Stick  synced  Synced. Received 1 change, sent 0 files.
b show "$id"          # the note, with both tasks
```

The CLI has no edit command, so this makes a conflict with the same Keep note,
imported with different text on each side (the same `createdTimestampUsec` gives the
same note id):

```sh
cat > "$scratch/keepA/list.json" <<'EOF'
{"title": "Packing", "textContent": "passport\ncharger", "createdTimestampUsec": 1600000000000000, "userEditedTimestampUsec": 1600000100000000}
EOF
cat > "$scratch/keepB/list.json" <<'EOF'
{"title": "Packing", "textContent": "passport\nsunscreen", "createdTimestampUsec": 1600000000000000, "userEditedTimestampUsec": 1600000200000000}
EOF
a import "$scratch/keepA" && b import "$scratch/keepB"
a sync; b sync; a sync
a conflicts           # f33ac77d-...  conflict  Packing
b conflicts           # the same line
a conflicts f33ac77d  # shown: passport, sunscreen; other: passport, charger
ls "$scratch/stick/jotter/formats"   # 1-json+gzip.json
```

Then unplug the "stick":

```sh
mv "$scratch/stick" "$scratch/away"
a sync                # Stick  unreachable  Not found (... is missing). If it is on a USB
                      # stick or another drive, plug it in. Nothing is synced until it is
                      # back.  Then: jotter: 1 of 1 backends did not sync, status 1
a backends status     # reachable: no, last-success: the earlier time
mv "$scratch/away" "$scratch/stick"
a sync                # synced, sent 1 file: B's record of the conflict, relayed
```

Refusals that need no server:

```sh
echo pw | a backends add webdav http://192.0.2.1/dav/ --user me
    # jotter: Cannot use http://192.0.2.1/dav/: Plain http would send the password and
    # every note unencrypted. Use https, or http to this machine only ..., status 1
echo tok | a backends add peer 192.168.1.10
    # jotter: 192.168.1.10 is not on your tailnet or this machine. ..., status 1
echo tok | a backends add peer 127.0.0.1:9 --password-in-file
    # jotter: Cannot reach the hub at 127.0.0.1:9: ... Connection refused ..., status 1
a backends remove "$(a backends | cut -f1)"
    # Removed Stick (...). Its files stay in .../stick: other devices can go on syncing
    # there, and Jotter never deletes them. ...
```

A failed add stores nothing: `$XDG_CONFIG_HOME/jotter` did not exist afterwards.
Remove the scratch directory with `rm -r "$scratch"`, and start a new shell for
Gradle, as `HOME` now points into it.

## Decisions made

ADR-0015, 0016 and 0017 are Proposed: written and reviewed by agents, not accepted by
the maintainer. Decisions marked **(orchestrator)** were made by the orchestrator on
the maintainer's behalf, for review at the end of the project
([PLAN.md §9](../PLAN.md#9-development-model-agent-swarm)).

Scheduling and secrets:

- **(orchestrator)** Without an ADR, in [PLAN.md §6.3](../PLAN.md#63-sync-cycle-per-backend)
  and the [`app:sync` README](../../app/sync/README.md): a local folder that cannot be
  reached is tried every 30 s, with no longer backoff, because that is only a look at
  the disk, and a USB stick should sync within 30 s of being plugged in. Other backends
  back off from 30 s, doubling to 30 minutes, and a refused password waits 30 minutes
  at once (`SyncTiming`).
- **(orchestrator)** Same place: a backend that is back syncs at once, on its own,
  without waiting for the next 5-minute round, both when its wait ends and when the Sync
  screen finds it reachable.
- **(orchestrator)** [ADR-0016](../adr/0016-where-secrets-live.md): passwords and
  tokens go in the Secret Service through `secret-tool`, with the secret on stdin or
  stdout and D-Bus autolaunch disabled, so it fails closed. A plain-text file created
  0600 in a 0700 directory, `$XDG_CONFIG_HOME/jotter/secrets.json`, is used only when
  the user chooses it, after no keyring answered. Never the database, a log, an
  argument or the environment, because the database goes into backups and bug reports.
- **(orchestrator)** Without an ADR, in `SecretServiceStore` and `BackendFactory`
  (`app:sync`): `secret-tool lookup` exiting 1 with no output means "nothing found" or
  a dismissed unlock prompt, and `secret-tool` does not say which. Jotter reads it as
  no secret and says "the keyring may be locked, or the password is missing", and never
  overwrites, deletes or forgets anything because of it. ADR-0016 does not record this
  case: it mentions a dismissed prompt only as an error that offers no fallback file
  when a backend is added.
- **(orchestrator)** Without an ADR, in the [`app:cli` README](../../app/cli/README.md)
  and `BackendsScreen`: removing a backend deletes its secret first, and removes nothing
  if that fails, so no password is left behind unseen. "Remove anyway" in the app, and
  `jotter backends remove --keep-secret`, remove it all the same and say where the
  secret stays and how to delete it, so that a locked or missing keyring cannot keep a
  backend for ever.

The hub:

- **(orchestrator)** [ADR-0015](../adr/0015-pc-hub-peer-protocol.md): the client sends
  its token only to loopback, `100.64.0.0/10` or `fd7a:115c:a1e0::/48`, checked on the
  address it connects to, with no opt-in, because the hub speaks plain HTTP and only
  WireGuard encrypts it. The hub binds only to loopback or a `100.64.0.0/10` literal.
- **(orchestrator)** ADR-0015, "The hub's socket layer": the hub uses the JDK's blocking
  sockets, one thread per connection, and the `server` module is JVM-only. The first
  version on Ktor's raw sockets could not close a socket for real: in review, 40 clients
  that never read left descriptors, about 450 to 500 MiB of heap and about 700% CPU
  behind. This amends ADR-0006 for `server`; `backend:peer` stays multiplatform.
- **(orchestrator)** ADR-0015, "Limits": at most 8 connections from one address, of 16
  in all, so that one tailnet node cannot take every slot. Further ones are closed at
  once.
- **(orchestrator)** ADR-0015, "Authentication": a token per device, made only on the
  PC (`PeerHub.pair`) and shown once, so there is no pairing over the network to
  attack and a lost phone is unpaired alone. The hub keeps only the SHA-256 of each
  secret, which cannot be guessed at 244 bits, so the token file holds nothing worth
  stealing, and checks it in constant time before reading the request.
- **(orchestrator)** ADR-0015, "How it runs": the hub runs inside the desktop app,
  started at launch if the user turned it on, on port 47734 by default, so there is no
  second process or service file. A systemd user service is left for later.
- **(orchestrator)** ADR-0015, "The backing store": the PC syncs with the hub's folder
  directly, as a local folder backend, not through HTTP. So the PC is one more device
  on its own hub, and relays between it and its other backends.
- **(orchestrator)** ADR-0015, "Transport and protocol": one request per connection,
  and no retries or redirects in the client. That keeps keep-alive and pipelining out of
  the server, so every limit is per connection, and sync already retries a failed
  `writeNew` as `BlobStore` asks. It costs a TCP handshake per file.
- **(orchestrator)** ADR-0015 and [ADR-0017](../adr/0017-webdav-backend.md):
  `UnreachableReason.UNAUTHORIZED` is a reason of its own in `backend:api`, not
  `FAILED`, so sync stops retrying a password or token that cannot work and the UI asks
  for a new one.

WebDAV and the format:

- **(orchestrator)** ADR-0017, amending ADR-0004: the format file's path names its
  format and codec, `jotter/formats/1-json+gzip.json`, so that like every other file a
  path has one content. On Apache, two versions could otherwise both write
  `format.json`, the later replacing the earlier. A backend holding another version's
  file is `Incompatible`. Nothing had shipped, so nothing migrates.
- **(orchestrator)** ADR-0017: adding a WebDAV store writes a test file twice and
  refuses a server that does not answer 412 the second time, such as `rclone serve
  webdav`, because there any retry could replace a file. Checked once, at setup.
- **(orchestrator)** ADR-0017: `list` is `PROPFIND` with `Depth: 1`, one collection at
  a time, never `infinity`, because every server must support depth 1 and lighttpd and
  Apache refuse `infinity` by default. The layout is shallow, so it costs one request
  per device folder.
- **(orchestrator)** ADR-0017, "Transport": Basic authentication on every request,
  with app passwords recommended; up to three attempts for a failed connection or 429,
  502, 503 or 504, after 0.5 s and then 1 s, or the server's `Retry-After` up to 30 s; and
  redirects followed only within the same scheme, host and port, at most 5, so the
  password never goes to another server.
- **(orchestrator)** ADR-0017: `https` only, except `http` to loopback, which the tests
  use, so a password and notes never cross a network in the clear. A NAS on plain
  `http` is refused.
- **(orchestrator)** ADR-0017 and the [`backend:webdav` README](../../backend/webdav/README.md):
  CI's lighttpd is Debian's 1.4.79 from `snapshot.debian.org` at a fixed date, in a
  `debian:trixie-slim` image pinned by digest, because lighttpd has no official image
  and Alpine's repositories dropped the build the first pin used. A pinned third-party
  image was not tried: running one was refused by this machine's permission rules.
- ADR-0017: `writeNew` is `PUT` with `If-None-Match: *` and nothing more. Exactly one
  winner among racing writers is not promised where the server does not make that
  atomic, as on Apache; sync does not need it, because a path has one possible content
  ([ADR-0014](../adr/0014-sync-failure-handling.md)).

Process:

- **(orchestrator)** Without an ADR: PRs #10 to #13 were merged with merge commits, not
  rebased or squashed, on 2026-11-03. The stacked branches contained merge commits of
  their own (for example `Merge m4/webdav into m4/integrate` and
  `Merge origin/m3/core-sync into m3/conflict-ui`), which a rebase would have had to
  rewrite.

## Known limitations and what was not verified

What has not been verified:

- **mailbox.org**, and so the exit criterion. Nor Nextcloud, ownCloud or any NAS.
- **TLS, against any server.** Every WebDAV test is plain `http` to 127.0.0.1. Whether
  Ktor's CIO can do TLS on `linuxX64` at all is unknown.
- **A real tailnet.** Every hub test is on loopback. MagicDNS names, an Android client
  and the claim that WireGuard makes TLS unneeded were not tested.
- **A real keyring.** No keyring daemon is installed here. `SecretServiceStore` ran
  against a stand-in `secret-tool` and against the real one on a private bus with no
  keyring, which shows it fails closed. Storing a secret in GNOME Keyring, KWallet or
  KeePassXC, and an unlock prompt, were never tried.
- **Android.** No device run. `backend:webdav` and `backend:peer` ran their tests on
  the Android host JVM only, not on Android's network stack.
- **The desktop app in a window.** Not opened since M2. The Sync screen, the hub
  controls and the dialogs ran only headless, with `runComposeUiTest`.
- **Apache's race.** Two writers of one path can both get `201` on Apache;
  `ApacheContractTest` skips the contract test that shows it. Harmless for sync,
  unsafe for any future use of `writeNew` with different content on one path.
- **`check`'s length.** 30 m 44 s on CI at `a8936ce`, against the 27.5 minutes in
  `ci.yml`'s comment and a 45-minute timeout. It grows with each milestone.
- **The nightly.** It reached `main` with PR #12 and has not run yet.
- **IPv6 and proxies.** The hub listens on IPv4 only. No proxy, captive portal or IPv6
  WebDAV server was tried.
- **The systemd user service and `jotter hub`** do not exist (ADR-0015).

Known limitations:

- `100.64.0.0/10` is also carrier-grade NAT space, so a PC on some networks can hold
  such an address outside the tailnet; the user must use the address Tailscale shows.
  The hub must never be exposed past the tailnet (no Funnel, Serve or port forwarding).
- The hub opens a connection per request, buffers whole answers (up to twice a file in
  memory) and holds at most 4 files at once. Slow clients on several addresses can hold
  every slot until their deadline. A pairing token is long to type on a phone.
- `secret-tool` must be installed (`libsecret`, or `libsecret-tools` on Debian). Over
  SSH or in cron there is usually no session bus, so the password file is the only
  choice there, and it is plain text.
- The `If-None-Match` probe proves the sequential case only, once. A server that
  changes later is not noticed.
- WebDAV names are not Unicode-normalised, and the `PROPFIND` walk is one request per
  device folder, in turn.
- The CLI prints three `SLF4J(W)` lines on stderr when it contacts a WebDAV server or a
  hub, as no SLF4J provider is on its classpath: checked with `backends add webdav` to
  an `https` URL and `backends add peer 127.0.0.1:9`. A refusal before any contact,
  such as plain `http`, prints none. The desktop app was not run, so whether it prints
  them too is not known.
- The CLI has no edit command, so the CLI alone cannot make or answer an ordinary
  conflict; answering is the desktop app's.

## What M5 (Android) needs from M4

- **A `SecretStore` on Android**, with a key from the Android Keystore (ADR-0016 leaves
  it to M5). `SecretServiceStore` and `SecretFileStore` are JVM, Linux only.
- **Scheduling.** `SyncScheduler` is the desktop's coroutine timer. Android maps the
  same rules onto WorkManager (15 minutes at least, network-constrained), including
  `UNAUTHORIZED` waiting for a new password rather than retrying.
- **The Sync screen on Android.** `BackendsScreen` is in `app:shared-ui`, but its hub
  controls (`PeerHubControls`) are JVM only: a phone adds the hub, it does not run one.
  The phone needs a way to enter the PC's Tailscale address and a long token; a QR code
  or link format is still open (ADR-0015).
- **TLS on Android**, untested: the WebDAV leg of M5's exit criterion needs `https`
  through Ktor's CIO on Android.
- **The hub over a real tailnet**, with the PC's hub bound to its Tailscale address and
  a phone as the client: the other leg of M5's exit criterion.
- **The device tests** that M3 left open: `fcntl` locks and `content://` folders for a
  local folder on Android, and the disabled Android host tests of `core:sync`,
  `core:storage` and `app:shared-ui`.
- **The mailbox.org run** above, ideally before M5, so that M5's WebDAV leg starts from
  a server known to work.
